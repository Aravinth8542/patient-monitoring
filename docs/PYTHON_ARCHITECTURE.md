# Python application and deployment architecture

Open `python_system_architecture.drawio` in [diagrams.net](https://app.diagrams.net/) for the editable, zoomable system diagram.

## Request lifecycle

1. FastAPI (`app/main.py`) mounts routers under `app/routers/`: `ingestion`, `alerts`, `aggregates`, `patients`, `staff`, `audit`, and `fhir`.
2. `app/clock.py` supplies the effective current time: normal UTC or `X-Test-Now` in TEST_MODE when supplied.
3. `app/security/` and authentication services establish device or staff authorization and database tenant context.
4. `app/services/` validates, normalizes, persists, and reevaluates observations/alerts.
5. PostgreSQL applies row-level security, transactional constraints, authorization functions, and audit controls.

## Ingestion pipeline

`POST /v1/devices/{device_id}/observations:batch` → device authentication → consent/tenant checks → idempotency handling → per-item normalization and clock-skew policy → observation persistence → aggregate refresh → observation-driven alert evaluation and missing-data reconciliation → per-item response.

The ingestion route does **not** run the complete time-only missing-data scan. That scan runs independently in the scheduler.

## Alerting and simulated time

- Normal operation: the scheduler runs a missing-data check every 300 seconds, without requiring HTTP requests. Normal GET alerts reads persisted alerts.
- TEST_MODE: API routes can use `X-Test-Now` as the effective server time. The **subsequently applied scoped replay patch** also evaluates the requested patient's missing-data state before GET alerts returns, when TEST_MODE is enabled and the header is present. This is a deliberate test-replay behavior, not a normal production GET side effect.
- Ingestion-based rule evaluation and late-data reconciliation are separate from the periodic time-only missing-data evaluation.

## Runtime containers

| Compose service | Purpose |
|---|---|
| `db` | PostgreSQL 17 with persistent named volume |
| `migrate` | One-shot Alembic migration runner, after database health |
| `seed` | One-shot development data seeding after migrations |
| `api` | FastAPI server, exposed on localhost port 8000 |
| `scheduler` | Independent missing-data job, interval `NO_DATA_INTERVAL_SECONDS=300` |

`api` uses `TEST_MODE: ${TEST_MODE:-0}`; `migrate`, `seed`, and `scheduler` use `TEST_MODE: "0"` in the inspected Compose file. The scheduler uses its real clock and is not synchronized to a request's simulated time.
